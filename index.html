How Ping data works

Slate's Ping script sits on selected web pages. Every time one of those pages loads in a browser, Slate writes one row. The export is a log of page views, not of people or visits. Visits and visitors have to be rebuilt from it.

One row = one page view

The URL that loaded, the page the visitor came from (referrer), a timestamp, and how long the page stayed open (duration, capped at 1 hour).

"Ping Identity" is a row number

Every value is unique across all rows, so it cannot group views by person. In production, the Person Reference ID fills that role once a browser is tied to a Slate record.

IP address stands in for a visitor

Here, visits are grouped by IP with a 30‑minute gap rule. School networks, iCloud Private Relay and mobile carriers put many people behind one IP, so visitor counts are approximate.

UTM fields are partly inferred

Only URLs carry real utm_ tags, yet rows have a UTM source. Slate fills Source/Medium from the referrer (for example Google → search) when no tag exists.

Methods

  • Sections are assigned from the URL path (e.g. /apply/frm, /apply/update, /apply/review → Application form; /apply/status → Status portal; /portal/reader_*, /apply/viewer → Staff tools).
  • Visits: consecutive page views from the same IP with gaps under 30 minutes.
  • Channels: from the referrer host plus UTM fields. Paid search needs a click ID (gclid, gbraid, gad_source) or a campaign name; other search engine traffic is organic.
  • Hidden when the toggle is on: Staff tools pages, IPs where 20%+ of views are staff tools (), and crawler‑like IPs (200+ views across 100+ distinct pages with a median of 3 seconds or less).
  • Excluded outright: rows from other hosts (Google Translate proxies, spam sites).
  • Weekly charts use Monday‑starting weeks; a week is included when it overlaps the date range.
